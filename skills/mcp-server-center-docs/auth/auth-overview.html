MCP 身份认证概览

作者: 飞超 · 更新时间: 2026-04-29
当前文档仅适用于 Aone MCP 网关上的 MCP Server。

当前文档不适用于 Interface Transform 类型。zetta 网关文档请移步：Welcome to ZettaGate

身份凭证

获取 MCP Server 地址后，MCP 客户端需要提供有效的 "身份凭证" 来连接 MCP Server 并创建 MCP 会话。

当前 Aone MCP 网关支持以下凭证类型：

  • 代码平台 Private Token
  • Aone MCP 网关颁发的 MCP OAuth Token
  • 应用可信身份

创建 MCP 会话时，客户端至少需要提供一种凭证。缺少有效凭证时，Aone MCP 网关将拒绝请求并返回 401 Unauthorized。

为什么需要凭证？
Aone MCP 网关需要记录 MCP 请求的来源身份（身份可以是 BUC 用户、OAuth 客户端、或是 Aone 应用），确保 MCP 流量可溯源、可审计、可管控。当发生异常调用时，我们可以通过请求来源身份快速找到相关责任人。

Private Token 鉴权

Private Token 是由代码平台颁发给 BUC 个人账号的凭证。MCP 客户端可以使用 Private Token 作为 BUC 个人身份凭证来创建 MCP 会话。

凭证传递方式

客户端可以在请求中添加 PRIVATE-TOKEN 请求头：

POST http://mcp.alibaba-inc.com/code/mcp HTTP/1.1
PRIVATE-TOKEN: ***********

对应的 mcp.json 如下：

{
  "mcpServers": {
    "code": {
      "url": "https://mcp.alibaba-inc.com/code/mcp",
      "headers": {
        "PRIVATE-TOKEN": "8sJH**********"
      }
    }
  }
}

客户端也可以通过 Bearer Token 进行传递：

POST http://mcp.alibaba-inc.com/code/mcp HTTP/1.1
Authorization: Bearer 8sJH**********

凭证获取方式

Private Token 可在以下页面获取：https://code.alibaba-inc.com/profile/account

注意事项

Private Token 可通过 Aone MCP 网关的鉴权校验，但不一定满足 MCP Server 本身的工具调用鉴权要求
  • 举个例子：Aone MCP 市场上有一部分 MCP Server 依赖 BUC OAuth token 进行免登，Private Token 无法用于生成免登 Ticket
  • 再举个例子：部分 MCP Server 使用其他授权服务器颁发的 token（例如该语雀 MCP Server）
当 Private Token 无法满足鉴权要求时，请使用标准 OAuth2 授权流程。

MCP OAuth 鉴权

Aone MCP 网关支持标准的 OAuth 授权流程：MCP 客户端对接该流程后，可以获取用户授权，安全地访问 Aone MCP 市场上的 MCP Server。

凭证传递方式

客户端通过 Bearer Token 传递 token：

POST http://mcp.alibaba-inc.com/code/mcp HTTP/1.1
Authorization: Bearer mcpa_xxxxxxxxxxxxx

凭证获取方式

MCP 客户端对接 OAuth 授权流程，完成用户授权后，可获取 mcpa_ 开头的 token（注意该 token 默认有 30 天有效期的限制）。

Aone MCP 网关当前支持以下两类客户端，开发者可以根据使用场景选择适合类型：

  • 标准 OAuth2.0 授权（授权码模式）
    • 接入文档：静态客户端接入指南
  • MCP 2025-06-18 协议版本 OAuth2.1
    • 适用于常见编程软件，例如 Cursor、Claude Code
    • 接入/使用文档：动态客户端使用指南

标准 OAuth2.0 适用于绝大部分内部客户端，例如 Aone Agent、OneDay。Aone MCP 网关会颁发 client_id 和 client_secret，客户端使用这些信息发起授权流程。

动态客户端则更适用于那些通用的 AI 编程软件，例如 Cursor、Claude Code 就实现了标准的 OAuth2.1 授权流程。动态客户端不需要提前获取 client_id/client_secret，可以通过标准协议对接多种不同来源的 MCP Server。

应用可信身份

客户端（Aone 应用）集成 Normandy Auth SDK，并在连接 MCP Server 时提供 SDK 生成的请求头，详见 系统间授权、Normandy Auth SDK 文档

适用场景：

  • 用户已在可信的系统或客户端软件中完成登录，例如阿里钉、Aone AI
  • MCP Client 与 MCP Provider 来自同一个团队或部门，Provider 信任来自 Client 的请求

「我该选择哪种鉴权方式？」

你是 MCP Server 用户

场景描述：你期望在某个 MCP 客户端中使用 Aone MCP 市场上的 MCP Server

  • 如果 MCP 客户端支持 OAuth 授权流程，则直接在客户端中发起授权
  • 如果 MCP 客户端不支持 OAuth，但允许你手动输入 Authorization Header 或自定义请求头，则建议使用 Private Token
    • 对于一小部分无法使用 Private Token 通过鉴权的 MCP Server，可访问该页面手动创建 token

你是 Agent 开发者

场景一：以某个固定的身份使用 MCP Server

  • 申请一个 BUC 公共账号，获取该公共账号的 Private Token
  • 在 Agent 中使用该 Private Token 连接 MCP Server 并调用工具

场景二：以用户身份调用 MCP Server

  • 申请 OAuth 客户端，当用户使用 Agent 时，发起 OAuth 授权流程并获取用户 token
  • 文档 → 静态客户端接入指南

场景三：不需要经过用户授权，以用户身份调用指定的 MCP Server

  • 应用可信身份
  • 文档 → 系统间授权

你是 MCP 工具的开发者

作为 MCP 工具的开发者，你在接入 MCP 网关时的一些选择会影响 "MCP 客户端与 MCP 网关" 之间的鉴权方式。例如启用 BUC 应用免登 后，MCP 客户端必须通过 OAuth 来连接 MCP Server。

"Aone MCP 网关与 MCP 工具提供方" 之间的鉴权能力详见 → MCP Server 接入指南
