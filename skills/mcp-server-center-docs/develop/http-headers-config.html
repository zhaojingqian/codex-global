HTTP 请求头配置

作者: 飞超 · 更新时间: 2026-01-25

默认情况下，网关（指 Aone MCP 网关）通过 HTTP/HSF 调用 MCP Tool Provider 时，仅传递部分必要的请求头，例如 EagleEye-TraceId、Authorization。为了方便开发者根据业务需求灵活传递请求头，网关支持开发者通过 mcp.headers 配置自定义请求头。

配置之前，请先阅读 调整 MCP Server 的选项

配置规则

固定请求头

配置固定的请求头键值对，所有请求均会携带该 header。

示例：mcp.headers.My-Custom-Token=Bearer token_123456

动态请求头

  • 支持使用 $ctx.xxx 获取上下文变量，当前仅支持以下写法：
    • $ctx.user.empId 获取当前 BUC 用户工号（数字工号前不带 0）
    • $ctx.user.loginName 获取当前 BUC 用户域账号
    • $ctx.user.name 获取当前 BUC 用户花名（没有花名时用真名代替）
    • $ctx.headers.Custom-Header 获取客户端请求中的指定请求头（请求头名称不区分大小写）
  • 示例1：将当前操作人的工号，放到 Buc-Emp-Id 请求头中
    • mcp.headers.Buc-Emp-Id=$ctx.user.empId
  • 示例2：将客户端的 User-Agent 放到 X-User-Agent 中
    • mcp.headers.X-User-Agent=$ctx.headers.User-Agent
  • 示例3：透传 My-Biz-Token
    • mcp.headers.My-Biz-Token=$ctx.headers.My-Biz-Token

敏感字段加密

  • 使用固定请求头时，支持用 encrypted: 前缀设置敏感信息
  • 示例：mcp.headers.My-Authorization=encrypted:93119326bd3880052390d9daad79
  • 注意事项：
    • 加密过程需开发者主动操作，解密过程由 MCP 网关自动处理
    • 不同 MCP Server 加密时，会使用不同的 password 或 salt，一个 MCP Server 生成的密文不能被其他 Server 所解密
    • 同一个 MCP Server，预发和线上使用相同的 password 和 salt，即预发生成的密文可以在线上被解密
    • 密文中包含 IV（初始化向量），相同输入 每次加密都会产生不同的密文
  • 其他：
    • 建议通过页面中的 "请求头配置" 进行加解密操作，避免出错
    • token、AK/SK、密码、cookie 等敏感信息，强烈建议进行加密

注意事项

  • 固定请求头（包括敏感字段加密）会出现在每一个请求中，包括获取工具列表的请求以及调用工具的请求；而动态请求头仅在调用工具时才提供。
  • 动态请求头涉及对表达式进行解析求值，当表达式解析出错时，或是表达式计算后的值为空（null）时，网关将不传递该请求头
  • 网关自动添加的请求头（例如鹰眼 EagleEye-TraceId）的优先级高于自定义请求头
    • 在添加自定义请求头时，尽量避免通用的请求头名称
    • 2025-01-23 更新：支持开发者配置 mcp.headers.Authorization，网关会将 Authorization 传递给 Tool Provider
  • 自定义请求头在不同接入类型下有一些差异
    • 通过 HSF 接入时，网关会通过 LiteMcpSchema.CallToolRequest 来传递 headers，具体获取方式详见 Java Aone MCP 研发手册
    • 通过 HTTP 或 Open API Transform 或代理已有 MCP Server 接入时，网关发起的 HTTP 请求中将携带自定义请求头
    • Stdio 托管类型暂不支持自定义请求头
  • 注意 HTTP 请求头本身是不区分大小写的，所以 "你配置的 header 名称" 和 "实际代码中获取的 header 名称" 的字母大小写可能不同
    • 以 Midway FaaS 为例，代码中读取到的请求头名称统一为小写字母
